# CPU helper comparison: FP16 versus the existing Q4 helpers

**Recommendation:** keep Qwen 4B for short triage and Qwen3-Coder 30B for supervised
coding when RAM permits. The tested FP16 models did not establish a better default.
The 7B model did produce a correct motor function after one plain-Python request,
so output format matters as well as model choice.

## Fresh first-pass results

Windows, i7-9700, 32 GB DDR4, CPU inference, Ollama 0.40.16. Four generation
threads, 2,048 context, temperature zero, thinking off, 640 output tokens and a
300-second request timeout. Every task required a JSON answer. One inference
request at a time; models were unloaded between requests.

| Cached model | Weights | HTTP triage | Motor cases /49 | Elapsed-time cases /46 | Four-task wall time | Lowest sampled available RAM |
| --- | --- | --- | --- | --- | --- | --- |
| Qwen2.5-Coder 0.5B FP16 | 0.99 GB | Failed | Invalid source | Invalid source | 19 s | 18.56 GiB |
| Qwen 3.5 4B Q4_K_M | 3.32 GB | Passed | 42 | 23 | 199 s | 15.19 GiB |
| Qwen2.5-Coder 7B FP16 | 15.24 GB | Failed | Invalid source | 24 | 543 s | 4.23 GiB |
| Qwen3-Coder 30B Q4_K_M | 18.56 GB | Not scored | Not scored | Not scored | Stopped by RAM guard | Below 2 GiB guard |

Package sizes are decimal GB; RAM figures are GiB. Invalid source was inspected
but not executed or assigned a numerical test score. The 0.5B model's fast time
includes function headers without bodies, not completed coding work.

The 30B trial initially failed admission at 18.5 GiB available. A later attempt
started at 19.53 GiB but hit the supervisor's two-GiB reserve guard before the first task result.
It was stopped before producing a score, and the shared API was restored idle.
The cleanup controller encountered a PowerShell capture timeout before saving
its RAM samples; the exact minimum and comparable wall time are unavailable.
Do not interpret the admission estimate as a guarantee of peak memory use.

## One corrective attempt, reported separately

- **0.5B FP16 motor:** still returned only a function header; no executable result.
- **4B Q4 motor:** improved from 42/49 to **47/49**; mixed OFF/unknown proof still failed.
- **4B Q4 elapsed time:** the correction exhausted its 640-token response budget;
  it was not scored as a complete implementation.
- **7B FP16 motor:** a corrective request for plain Python, without the JSON-format
  constraint, returned code that passed **49/49** after removing only Markdown
  fences. It took **191.55 seconds**. The elapsed-time function was not retried.

That last probe changed both the format request and feedback, so it does not
isolate a formatter defect. It shows why the helper now has an explicit
`ask --response-format text` option. Receipts remain JSON, drafts stay in `content`,
and no code is executed or accepted automatically. JSON mode never silently
downgrades to text.

## Reference for the 30B helper

The November 21 experiment on the same cached 30B model scored **49/49 motor and
42/46 elapsed time: 91/95 first pass**. One targeted elapsed-time correction
reached **95/95**. It failed the exact HTTP-triage verdict and supplied a workable
portable-helper packaging fix. That run used eight threads and a different
system wrapper, so its timings are not a direct comparison with today's runs.

## What failed and what the timings mean

The 0.5B JSON answers omitted function bodies. The 7B JSON motor answer ended
inside a Python string. Its elapsed-time draft mishandled duplicates and input
validation. The 4B elapsed-time draft extrapolated after the final sample and
counted inactive intervals. None of these drafts qualifies production logic.

All three fresh import proposals failed review. An isolated, trusted fixture
confirmed that copying a real helper to the parent directory still imports the
already-cached wrapper recursively; replacing the exported wrapper with the
real helper works. This control is now an offline repository test.

Measured generation throughput was approximately **20.1 tokens/s** for 0.5B,
**6.6** for 4B and **1.7** for 7B FP16. Throughput alone does not measure useful
work: the smallest model emitted very little valid code. Per-task latency also
includes model reloads. The user reported no noticeable VS Code lag during the
four-thread trials; no instrumented UI-latency test was performed.

This is one sample per model/task, not a general model leaderboard or a controlled
quantization study. Model families and sizes differ. Early trials overlapped the
7B download; background activity and Windows file cache were not controlled.
The 7B download needed a resumed request after a near-completion timeout; the
cached F16 manifest was verified before inference.

## Reproduce

The first-pass protocol used repository commit
`52a7b40d37dda4122159b35259c1a8f7c6d8a265`, with four synthetic tasks and 95
hand-derived coding cases. Hand-written controls pass every case. Generated
source was reviewed before hash-pinned execution in a bounded child process.

```sh
python -m local_worker_bench run --model EXACT_CACHED_TAG --tasks http motor elapsed import --threads 4 --context 2048 --max-tokens 640 --timeout 300 --output results/new-trial
```

Add `--endpoint` and `--allow-lan` for a private LAN server. Check RAM first: the
portable client does not monitor server memory; this experiment used an additional
local supervisor. It never closed work apps. Raw drafts/logs remain in the local
temporary evaluation directory, not in git. No application/customer data was used.

Cached model digest prefixes: 0.5B `06760f570b0a`, 4B `d8b0f5e9760c`,
7B `9bff1b5c46f8`, 30B `06c1097efce0`. Defaults remain unchanged. Both FP16
candidates remain cached for further experiments; all models were unloaded at
the end and the LAN API was left running idle.
