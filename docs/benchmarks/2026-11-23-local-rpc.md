# Native three-node RPC practice: measured coding quality and cost

Date: 23 November 2026. One Windows PC, Intel i7-9700, approximately 32 GiB RAM,
CPU only. Real native remote-device execution on loopback; not three physical
8 GiB computers. All inference processes created by these trials were stopped.

## First-pass coding grades

| Model / configuration | Motor | Elapsed-time logic | Combined |
| --- | --- | --- | --- |
| Qwen3.5 4B, single process, 4 threads | 42/49 | 28/46 | 70/95 |
| Same 4B, three RPC CPU devices, 1 thread each + 1 coordinator | 34/49 | 28/46 | 62/95 |
| Same 4B, single process, 1 thread control | 34/49 | Not run | Not a 95-case result |
| Historical Qwen3-Coder 30B Q4, single worker, 4 threads | 49/49 | 39/46 | 88/95 |

These are first drafts. No repaired answers or human edits are folded into the
scores. The controls cover 49 motor-proof cases and 46 elapsed-time cases, not
95 independent coding projects. Many cases exercise validation behavior.
The model received the synthetic specification, not a test execution tool.
Source was inspected before the exact-hash checker executed it.

The 4B motor drafts mishandled unknown proof states. The RPC/one-thread draft
also accepted invalid proof collections instead of raising ValueError. Both
4B elapsed drafts rejected actual Boolean fault/active values, failing normal
inputs. The saved 30B elapsed draft handled ordinary intervals better but failed
duplicate handling and numeric validation. Passing partial fixture totals is
not autonomous coding reliability.

## Inference timing

Wall time below is the request time with the model already loaded. Load/startup
time is reported separately. Output lengths differ, so wall time alone is not
a normalized speed metric. Generation rates are the native engine's reported
rates; prompt evaluation is separate.

| Configuration | Task | Wall seconds | Prompt seconds | Generated tokens | Generation tok/s |
| --- | --- | ---: | ---: | ---: | ---: |
| 4B single, 4 threads | motor | 59.756 | 7.111 | 335 | 6.349 |
| 4B single, 4 threads | elapsed | 105.285 | 8.849 | 588 | 6.089 |
| 4B three-node RPC | motor | 110.532 | 24.691 | 269 | 3.123 |
| 4B three-node RPC | elapsed | 229.748 | 35.417 | 593 | 3.047 |
| 4B single, 1 thread | motor | 96.686 | 22.264 | 269 | 3.602 |

The 4B RPC smoke request returned exactly `READY`: 17.962 seconds load/startup,
3.427 seconds request time, 21.929 seconds for the complete owned-process run.
That proves response plumbing, not coding quality.

The historical 30B motor request took 161.515 seconds and elapsed took 245.247
seconds, including separate native loads of 14.428 and 13.038 seconds. Their
generation rates were about 2.925 and 3.059 tokens/second. This is a quality
reference from 22 November, not a controlled speed comparison: different model,
tokenizer and facade, with cold process loading per request. The prompt text
hashes match the current motor/elapsed tasks.

## Resources and lifecycle

Sampled every 0.25 seconds; samples can miss short peaks. Aggregate RSS sums
process working sets and can double-count shared pages. It is not isolated
physical model memory. Host free RAM also reflects other applications and cache.

| Run | Load/startup seconds | Entire run seconds | Peak aggregate RSS GiB | Minimum host free GiB | Owned processes stopped |
| --- | ---: | ---: | ---: | ---: | --- |
| 4B RPC smoke | 17.962 | 21.929 | 5.294 | 9.611 | Yes |
| 4B single 4-thread, both coding tasks | 15.803 | 181.187 | 2.770 | 10.994 | Yes |
| 4B RPC, both coding tasks | 17.600 | 358.375 | 5.456 | 10.129 | Yes |
| 4B single 1-thread, motor only | 9.060 | 106.081 | 2.762 | 12.925 | Yes |

RPC coding run per-process peak RSS: node 0 **0.809 GiB**, node 1 **0.798 GiB**,
node 2 **1.237 GiB**, coordinator **2.613 GiB**. The coordinator and node 0 are
the proposed logical worker 1; they are two processes on this same PC.

All requests used 2048 context, 1024 maximum output tokens for coding, temperature
zero, non-thinking mode and JSON format. A run kept weights loaded between its
tasks. Native prompt cache reported zero cached tokens. Equal RPC split inputs
produced decoder blocks 0-10 on RPC0, 11-21 on RPC1, and 22-31 on RPC2. Logged
assignment slot 32 is output placement, not a 33rd decoder block. Input embedding
remained host-side. Each remote log contains graph execution events; reuse is
not fully logged, so event counts are not total RPC calls or tokens.

## What the threading control tells us

The 1-thread single-process and RPC motor candidates have the exact same SHA-256:
`bc2ea36f08e34d7d14739901a9a50b2b41b446194ff57c4a512d1c6127cebb64`.
They also have the same output-token count and 34/49 score. The RPC request was
about **14.3% longer** than this one-thread control, versus about 85% longer
than the four-thread motor baseline with a different answer.

This supports a threading/numerical explanation for the motor text difference;
it does not establish bitwise equivalence for all tasks, logits, architectures
or machines. The one-thread control did not run elapsed. Graph partitioning,
thread placement and verbose logging all affect timing; this is not a pure
Ethernet overhead test or a repeated statistical benchmark.

## 80B preparation, without an unsafe inference escalation

All four official Qwen3-Coder-Next Q4_K_M parts are present, with the downloader's
completed SHA-256 verification record. Total disk bytes: **48,410,992,032**
(48.41 decimal GB / about 45.09 GiB).

`plan_gguf_partitions.py` read the actual tensor directories without reading
weight payloads into RAM. It minimizes the largest contiguous serialized group,
placing input embedding in group 1 and remaining non-block output tensors in 3:

| Storage group | Decoder layers | Serialized span bytes | GiB |
| --- | --- | ---: | ---: |
| Worker 1 | 0-15 | 16,305,284,096 | 15.185 |
| Worker 2 | 16-31 | 15,575,794,688 | 14.506 |
| Worker 3 | 32-47 | 16,523,926,528 | 15.389 |

This is a real directory-based **plan**, not completed distributed 80B inference.
Spans include padding and exclude file metadata; OS, cache, workspace and runtime
are extra. The parts exceed the proposed 8 GiB and 16 GiB host inference budgets.
Three 32 GiB hosts are a more plausible resident target, still unverified.
Three processes on one 32 GiB PC do not add memory. The practice harness refuses
model files over 6 GiB, so it did not launch 80B. Explicit disk-backed RPC is
still engineering work; stock RPC allocation alone does not provide it.
